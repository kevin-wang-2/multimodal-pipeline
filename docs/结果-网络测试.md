# 网络吞吐排查（2026-09-10）

起因：Mac → seanartech-lab 传 3.75GB 的 CUDA 包只有 ~4.5 MB/s，怀疑链路。

工具：`tools/nettest.sh`（Mac 发起，只依赖两端 ssh + cat/head）

## 三目标对照（200 MiB/次，x1 与 x4 并发）

| 目标 | 路径 | 上传 Mac→X | 下载 X→Mac |
|---|---|---|---|
| 老笔记本 `192.168.71.201`（Realtek 1G，直连交换机） | 不经 Hyper-V | **93.8 / 107.7 MB/s** | 11.8 / 47.3 MB/s |
| seanartech-lab 主机 `192.168.71.200` | 经 Hyper-V external vSwitch | 27.7 / 36.6 MB/s | 7.8 / 31.3 MB/s |
| VM `100.64.0.6`（Linux，同主机内，**同一物理口**） | 经同一 vSwitch | 28.6 / 33.6 MB/s | **56.2 / 64.4 MB/s** |

（单位 MB/s；x4 是合计吞吐）

## 结论

1. **Mac 侧完全没问题**：上传能打满 1G（107.7 MB/s = 861 Mbit/s）；经 Linux 目标下载可达 64 MB/s。
   → Mac 那块 USB 2.5G 网卡（`en6`，协商 2500Base-T）和交换机路径都没问题。
2. **seanartech-lab 主机的网络路径明显偏慢**：上传只到 ~28 MB/s。
   而**同一物理口**上，Hyper-V 里的 Linux VM 下载能到 64 MB/s、上传 33 MB/s。
   → 瓶颈在 **Hyper-V external vSwitch ↔ 主机虚拟网卡** 这一段，不在物理链路。
3. **Windows 目标的「下载」普遍慢**（8–12 MB/s），Linux 目标 56 MB/s。
   → 指向 Windows OpenSSH 的发送路径 / MSYS 管道（测量偏悲观），或主机 vNIC 的接收路径。
4. 早期测到的 11 MB/s 更保守，可能包含当时上联未修好的因素；用户已定位到「交换机1↔交换机2 上联段」。

## 建议

- 往训练机搬大数据/模型，**别用 scp**。优先 SMB 共享（Windows 原生栈）、或 Gitea/LFS（走 Caddy/HTTPS）。
- 主机侧可研究：Hyper-V vSwitch 开 VMQ / SR-IOV；或训练数据传输时用一块不绑 vSwitch 的独立网卡。
- 复测命令：`tools/nettest.sh seanartech-lab` / `tools/nettest.sh lenovo@192.168.71.201`

## 测量口径提醒

`nettest.sh` 的远端只用到 `cat`/`head`（Windows 上是 Git Bash），**Windows 目标的数字偏悲观**——
它测的是 "ssh 隧道 + MSYS 管道" 的端到端吞吐，不等于纯网络能力。要测纯网络请用 iperf3。
