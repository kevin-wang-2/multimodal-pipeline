# 协议 v1.0

> 状态：S0 定稿（2026-09-19）。本文是 [`protocol/schemas/`](../protocol/schemas/) 的人读版；**两者不一致时以 schema 为准，并修本文**。
> 设计背景见 [架构.md](架构.md) §4–§10；本文只讲"到底长什么样、边界在哪"。

## 0. 版本与变更

- 五个 schema，JSON Schema 2020-12，`$id` 为 `urn:mmp:protocol:<major>:<name>`：

  | `$id` | 内容 | 根 |
  |---|---|---|
  | `urn:mmp:protocol:1:ab-message` | A↔B 信封与四类 payload | 信封 |
  | `urn:mmp:protocol:1:job-api` | C→B 任务 API 的请求 / 响应体 | 无根，只有 `$defs` |
  | `urn:mmp:protocol:1:media-handle` | 媒体句柄 | 句柄 |
  | `urn:mmp:protocol:1:digest` | 预检产出 | digest |
  | `urn:mmp:protocol:1:capability` | 任务类型元数据 | 一条能力 |

- `protocol_version` 形如 `"1.0"`。**major 不同 = 不兼容**，B 直接拒绝（§2.3）；minor 只做向后兼容的追加（新可选字段、新枚举值）。
- 所有对象默认 `additionalProperties: false`。想加字段先改 schema、加 fixture、两侧测试过，再写代码。
- 依赖方向：`ab-message → job-api → {capability, media-handle}`，`digest → {job-api#Source, media-handle#MediaId, capability#TaskTypeId}`。无环。

## 1. 标识符

| 名字 | 格式 | 谁生成 | 备注 |
|---|---|---|---|
| `node_id` | `^[a-z0-9][a-z0-9-]{0,62}$` | 部署配置 | A 的名字 |
| `job_id` | `<node_id>-<ULID>` | **A** | B 无状态，靠前缀把 GET / DELETE 路由回原节点；ULID 26 位 Crockford base32 |
| `media_id` | `sha256:<64 位小写 hex>` | A（取到字节后） | 也是缓存键的一部分；与来源无关 |
| 任务类型 id | `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$` | 注册表 | 点分命名空间（`triage.audio`），下划线分词（`pitch_transcribe`） |
| `req_id` | 任意字串 1–128 | **B** | 连接内唯一即可 |
| `protocol_version` | `^\d+\.\d+$` | — | 见 §0 |

## 2. A↔B 协议

### 2.1 信封

```json
{ "type": "register | heartbeat | request | response",
  "protocol_version": "1.0",
  "ts": "<RFC 3339>",
  "payload": { ... } }
```

一条 ws 连接、四类消息，A/B 绑定时同一信封走进程内调用。B 拒绝 A 时不发消息，直接关连接并带关闭码（§2.3）。

### 2.2 四类 payload

| type | 方向 | 字段 | 说明 |
|---|---|---|---|
| `register` | A→B | `node_id` `node_key` `capabilities[]` `engine_versions{}` | 连接后的**第一条**消息；重连必重发；B 用 `node_id` 覆盖旧表项。`capabilities` 每项是 §8 的能力；`engine_versions` 是引擎名→版本的汇总 |
| `heartbeat` | A→B | `node_id` `queue_len` `running` `engines_loaded[]` `vram_free_mb?` | **每 10s 一次，连续 3 次未收到视为断线**。无 GPU 的节点省略 `vram_free_mb` |
| `request` | B→A | `req_id` `op` + (`job` \| `job_id` `wait?`) | `op=submit` 带 `job`（= `POST /jobs` 请求体）；`op=get` / `op=cancel` 带 `job_id`，可带 `wait` |
| `response` | A→B | `req_id` `http_status` `body` | 与 HTTP 语义一一对应，B 把 `http_status` 与 `body` 原样透传给 C。`body` 是 §3.3 的任意响应体 |

### 2.3 连接生命周期

1. A 主动出站连到 B（A 零监听）。发 `register`。
2. B 校验：schema → `node_key` → `protocol_version` 的 major。任一失败**关连接**，关闭码：

   | 码 | 名 | A 的处理 |
   |---|---|---|
   | 4001 | `unauthorized` | 不重试，等配置变更 |
   | 4002 | `protocol_mismatch` | 不重试，等升级 |
   | 4003 | `bad_register` | 视为 bug，记日志后按退避重试 |

   连接在 register 后**保持打开即表示接受**；没有 ack 消息。
3. A 每 10s 发 `heartbeat`；B 收不到 3 次即：删表项、在途请求全部回 C `503 node_offline`。
4. B 发 `request`，A 回 `response`。B 侧**在途超时 = `wait` + 5s**（`submit` / `get` 按请求里的 `wait`，缺省 0）；超时同样回 C `503 node_offline`，并把该连接视为不健康关掉。
5. 任意原因断开后 A 重连：**指数退避 1s → 60s，抖动 ±20%**；重连即重新 `register`。
6. A 可同时连多个 B，每条连接独立走上面的流程；每个 B 只知道连到自己的 A（"能力表一致性"不是目标，B 的表就是此刻的视图）。

## 3. C→B 任务 API

### 3.1 端点

| 方法 | 路径 | 请求体 | 响应体（§3.3） |
|---|---|---|---|
| `POST` | `/jobs` | `JobRequest` | `JobResponse` \| `ErrorBody` |
| `GET` | `/jobs/{id}[?wait=N]` | — | `JobResponse` \| `ErrorBody` |
| `DELETE` | `/jobs/{id}[?wait=N]` | — | `JobResponse` \| `ErrorBody` |
| `GET` | `/capabilities` | — | `CapabilitiesResponse` |
| `GET` | `/health` | — | `HealthResponse` |

### 3.2 `JobRequest`

```json
{ "type": "triage.audio",
  "media": <MediaHandle, §5>,
  "params": {},                          // 该类型 input.params_schema 的实例；进缓存键
  "priority": "interactive | batch",     // 缺省 interactive
  "tier": "cpu | gpu-fast | gpu | remote", // 可选，档位偏好；不满足则回落并标注 degraded
  "wait": 0 }                            // 0–120 秒
```

`tier` 是顶层字段而不是 `params` 的一项：它对所有任务类型同义，且是缓存键的独立维度。

### 3.3 响应体

| HTTP | body | 何时 |
|---|---|---|
| 200 | `JobDone` `{job_id, type, status:"done", media_id, cached, source, result \| result_ref, timings_ms?}` | 完成（含缓存命中） |
| 200 | `JobCancelled` `{job_id, type, status:"cancelled"}` | 已取消 |
| 202 | `JobPending` `{job_id, type, status:"queued"\|"running", eta_sec?, queue_position?, cancel_requested?}` | `wait` 内没完成 |
| 4xx/5xx | `JobFailed` `{job_id, type, status:"failed", error, message?, retry_after_sec?}` | 任务入队后失败（HTTP 状态按 §4） |
| 4xx/5xx | `ErrorBody` `{error, message?, retry_after_sec?}` | 请求没被接受 / 找不到任务（HTTP 状态按 §4） |

规则：

- **`wait` 语义**：`POST` / `GET` 最多阻塞 `wait` 秒；期间完成则 200，否则 202。缓存命中与短任务在 `wait` 内直接拿到结果，不分同步 / 异步两套。
- **状态机**：`queued → running → done | failed | cancelled`；`queued → cancelled`。终态不再变化。
- **去重合并**：任务键 = (`media_id`, `type`, `tier`, `engine_version`, 规范化 `params` 的 hash)。同键任务在排队 / 运行中 → 返回**已有**的 `job_id`；已完成且在缓存 → 200 `cached: true`。
- **取消**：`DELETE` 对排队中任务直接出队 → 200 `cancelled`；对运行中任务置取消标记并尽力而为 → 202 `running` + `cancel_requested: true`，后续 `GET` 得 `cancelled` 或 `done`；对终态任务返回当前终态。
- **结果去哪**：`result` 内联；输出超过实现配置的内联上限且请求里给了 `media.put` → A PUT 过去，响应只带 `result_ref {content_type, bytes, sha256}`；没给 `put` 又超限 → `500 engine_failed`（message 说明）。
- **`type` 回显**在所有任务态响应里，消费方据此选 `result` 的 schema。
- 完成的任务能 `GET` 多久是 A 的配置（建议 ≥ 1h），过期 → `404 not_found`。

### 3.4 `/capabilities` 与 `/health`

- `CapabilitiesResponse {protocol_version, capabilities: [{capability, nodes: [node_id]}]}`：B 把已连接 A 的注册表按任务类型合并；同 id 不同节点视为同一能力（M1 不比对元数据差异）。
- `HealthResponse {status: "ok"|"no_node", protocol_version, nodes: [{node_id, connected_since, last_heartbeat, heartbeat?}]}`。

## 4. 错误码表

| `error` | HTTP | 谁发出 | 何时 | C 该怎么办 |
|---|---|---|---|---|
| `bad_request` | 400 | B 或 A | 请求体不符合 schema / `params` 不符合类型的 `params_schema` / 要求的 `tier` 该节点没有 | 修请求 |
| `unsupported_type` | 400 | A | 路由到的节点不认识 `type`（B 路由表与 A 注册表短暂不一致） | 重试一次，再不行当 `no_node` |
| `unauthorized` | 401 | B | C→B 认证失败（认证方式由部署决定） | 修配置 |
| `not_found` | 404 | A 或 B | 未知 / 过期 `job_id`；`job_id` 前缀对应的节点不在线时 B 也回 `503 node_offline` 而不是 404 | 重新提交 |
| `media_too_large` | 413 | B 或 A | `inline` 解码后 > 8 MiB | 改走 `get` |
| `media_fetch_failed` | 422 | A | `get` 端点不可达 / 非 2xx / 内容无法解析 | 检查句柄 |
| `backpressure` | 429 | A | 队列长度超上限；带 `retry_after_sec` | 按 `retry_after_sec` 重试或降为 `batch` |
| `engine_failed` | 500 | A | 引擎子进程崩溃 / 报错 / 输出超限无处放 | 重试或换 `tier` |
| `no_node` | 503 | B | 没有任何在线节点提供该 `type` | 兜底（铁律 5） |
| `node_offline` | 503 | B | 在途请求期间节点断线，或 A 在 `wait` + 5s 内未响应 | 重试；仍失败则兜底 |
| `timeout` | 504 | A | 任务超过类型时限且没有更便宜的档可回落 | 兜底或改 `batch` |

**不是错误**的两件事：

- **超时降级**：任务超时但有更便宜的档 → 用便宜档出结果，**200** + `source.degraded: true` + `degraded_reason: "timeout"`。
- **部分失败**：预检里某个工具失败但 digest 骨架能出 → 200 + `degraded_reason: "partial_failure"`，失败项在 `digest.tools` 里标 `failed`，缺口写进 `gaps`。

## 5. 媒体句柄

```json
{ "inline": "<base64>" }                                   // 或
{ "get": {"url": "https://…", "headers": {...}},
  "put": {"url": "https://…", "headers": {...}},           // 可选：大输出写回
  "content_type": "audio/wav" }                            // 可选提示
```

- `inline` 与 `get` **二选一**；`put` 只能伴随其一出现。
- `inline` 解码后上限 **8 MiB**，超过必须走 `get`。
- `url` 只允许 `http(s)`。presigned URL、宿主自带 token 的接口、将来 B 提供的上传口，都是同一契约的实例；A 只做 GET / PUT，不认识任何存储厂商。
- **本机路径不在契约里**（`{"path": …}` 会被 schema 拒绝）。三者同进程时的捷径是实现细节，不进接口。
- `media_id` 在 A 取到字节后计算：同一份媒体经 `inline` 与经 `get` 提交得到同一个 `media_id`，命中同一条缓存。

## 6. 结果的来源标注（`Source`）

```json
{ "tier": "cpu", "engine": "silero-vad+sensevoice-int8+zipformer-tagging-int8",
  "engine_version": "m0-2026-09-10", "generated_at": "<RFC 3339>",
  "degraded": false,                          // 必填；true 时 degraded_reason 必填
  "degraded_reason": "timeout | tier_unavailable | partial_failure",
  "params": {"label_confidence_threshold": 0.3} }  // 实际生效的参数（含默认值）
```

- `Source` 描述**产物本身**（谁、哪一档、何时、是否打折）。**`cached` 不在其中**：命中缓存是本次交付的属性，不是产物的属性，放在 `JobDone.cached`。因此 digest 独立存放时不带 `cached`（与架构.md 早期示例的差别，已同步修正）。
- `JobDone.source` 与 `result` 内部的 `digest.source` 内容相同；前者让非 digest 类型也有来源标注，后者让 digest 独立可用。

## 7. digest

字段与语义见 [架构.md §8](架构.md#8-digest-schema核心产出物)；这里只列 schema 把哪些话说死了：

- `kind` 在 v1 **只有 `audio`**；图片 / 视频（M4）作 minor 追加。`timeline_unit` 固定 `"sec"`，区间左闭右开。
- `segments[].label_status`：
  - `ok` → `labels` 非空，按 score 降序，全部 ≥ 阈值（`source.params.label_confidence_threshold`，默认 0.30）；
  - `unclassified` → top 分数 < 阈值，**`labels` 必须为空**，并在 `gaps` 写"分类置信度过低（top x < 阈值 y）→ 无法判定类别"；
  - `failed` → 打标工具在本段失败，`labels` 为空。
- `segments[].asr` 的三分法（T4 观察③）：
  - `null` = **不适用**（非语音段）；
  - **省略** = 应有但取不到（语音段 ASR 失败 → `tools.asr` 为 `failed` / `partial`，`gaps` 里说明）；
  - 对象 = 结果。对象内取不到的值用 `"n/a"`（`confidence`）或省略，**不用 `null`**。
- `global` 只有 `speech_ratio`；**没有 `caption`**。
- `tools` 的值只能是 `ok | partial | failed | skipped`。
- `capabilities_available` 项是任务类型 id。
- schema 管不到、**实现必须保证**的不变量：segments 覆盖 `[0, duration_sec)`、按 `start` 升序、互不重叠、`end > start`、`end ≤ duration_sec`。S2 的单测负责。
- M0 的样本：[`protocol/fixtures/digest/root/valid/m0_hum_then_speech.json`](../protocol/fixtures/digest/root/valid/m0_hum_then_speech.json)；T4 修正前的原始输出作为反例保留在 `invalid/t4_raw_before_fix.json`。

## 8. 能力元数据（`Capability`）

```json
{ "id": "ocr.structured", "modal": "document",
  "description": "一句话，给 agent 看",
  "consumes": {"labels": ["Humming", "Singing"], "granularity": "segment"},   // 可选，M2 用来筛 capabilities_available
  "tiers": [                                                                  // 按偏好排序，第一项是默认档
    {"tier": "gpu-fast", "engine": "pp-ocrv6", "engine_version": "paddleocr-3.7", "cost": "low",
     "latency_hint": "~0.5s/page", "vram_mb": 2048, "max_concurrency": 2},
    {"tier": "gpu", "engine": "paddleocr-vl", "engine_version": "1.6-0.9b", "cost": "high",
     "latency_hint": "~9s/page", "vram_mb": 12288, "max_concurrency": 1} ],
  "input": {"media": "required | optional | none", "params_schema": { ...JSON Schema... }},
  "output_schema": "urn:mmp:protocol:1:digest" }          // 或内联 JSON Schema
```

- 与架构.md §10 的 yaml 相比：`tier` / `cost` / `latency_hint` 下沉到 `tiers[]`（一个类型多档），加 `engine_version`（进缓存键）与 `vram_mb` / `max_concurrency`（调度用）；`start` / `end` 之类类型专有输入统一进 `params_schema`。
- `tier` 枚举：`cpu`（便宜档常开）/ `gpu-fast` / `gpu` / `remote`（A 转调外部服务）。架构.md §12 的 L0–L3 是预算阶梯的概念层级，不是这里的枚举。

## 9. 契约测试

```
protocol/fixtures/<schema>/<def>/{valid,invalid}/<name>.json
```

`<schema>` 对应 `schemas/<schema>.schema.json`；`<def>` 是 `root` 或该 schema 的一个 `$defs` 键。两侧 runner 走同一目录，valid 必须通过、invalid 必须失败：

```bash
# Python（jsonschema + referencing，格式校验开）
.venv/bin/pip install -r protocol/tests/py/requirements.txt
(cd protocol/tests/py && ../../../.venv/bin/python -m pytest -q)

# TypeScript（ajv 2020 + ajv-formats）
(cd protocol/tests/ts && pnpm install && pnpm test)
```

加规则的流程：改 schema → 至少一个 valid 与一个 invalid fixture → 两侧都过 → 改本文。invalid 样本的文件名就是它违反的规则。S1 起这两条命令进 CI 的 `unit` job。

## 10. 决定记录

S0 在架构.md / 实施计划.md 之上具体化或偏离的点，方便以后回看为什么：

| 决定 | 理由 |
|---|---|
| `media_id` 用完整 64 位 hex，不截断 | 它是缓存键，截断只换来歧义；架构.md §8 示例同步改 |
| `cached` 从 `source` 移到 `JobDone` 顶层 | 命中缓存是交付属性不是产物属性；避免同一 digest 存两份只差一个布尔 |
| `tier` 是 `JobRequest` 顶层字段 | 对所有类型同义、是缓存键独立维度；`params` 留给类型专有参数 |
| register 成功不回 ack，失败用 ws 关闭码 | 保持"四类消息"；连接开着即接受，少一个状态 |
| B 在途超时映射为 `503 node_offline`，不新增错误码 | 从 B 的视角"不响应"与"断线"无法区分，也不需要区分 |
| 新增 `timeout`(504)、`not_found`(404)、`bad_request`(400)、`unauthorized`(401)、`media_too_large`(413) | 计划里的表少了"超时且无处回落""查不到任务""schema 不合法"这几个必然出现的情况 |
| `timeout_degraded` 不是错误码 | 它是 200 + `source.degraded`，放进 `error` 枚举会误导 C |
| `wait` 上限 120s | B 的在途超时 = wait + 5s，长阻塞占连接；更长的任务走 202 + 轮询 |
| `JobDone` / `JobPending` / `JobFailed` 都回显 `type` | C 需要它选 result schema，B 无状态不能替 C 记 |
| `digest.kind` 只允许 `audio` | 没定义的东西不该能通过校验；M4 追加是 minor |
| `capability.tiers[]` 有序，首项为默认档 | 比单独的 `default_tier` 字段少一处可能不一致的地方 |
| 任务类型 id 同时允许点与下划线 | 沿用现有命名（`triage.audio` 与 `pitch_transcribe`），不为统一风格改既有名字 |
