# T1 结果 · seanartech-lab ASR 基线（CPU 部分）

> 2026-09-10 · whisper.cpp b4938 `whisper-bin-x64.zip`（CPU 构建）
> 机器：Intel Core Ultra 9 285K / 24 线程（本次 `-t 8`）/ 32GB DDR5-6000 单通道
> 素材：`testdata/m0_long_26s.wav`（4.4s 片段 ×6 = 26.3s，16kHz 单声道）
> 模型来源：hf-mirror.com/ggerganov/whisper.cpp（**注意：不是 `ggml-org/whisper.cpp`，那个 404**）

## 实测（CPU，8 线程）

| 模型 | 体积 | 加载 | encode | decode+batchd | 总计 | RTF | 倍速 |
|---|---|---|---|---|---|---|---|
| `ggml-base` | 147 MB | 99 ms | 243 ms | 262 ms | **735 ms** | 0.028 | **36×** |
| `ggml-large-v3-turbo` | 1.62 GB | 891 ms | 5363 ms | 563 ms | **6958 ms** | 0.264 | **3.8×** |

换算：1 小时音频 → base 约 **1.7 分钟**；turbo 约 **16 分钟**。

## 结论

1. **CPU floor 完全够用**（短音频）：base 36× 实时，比实时快一个数量级。
2. **"上 GPU" 的硬理由被量化了**：turbo 在 CPU 上只有 3.8×；**任何长音频/批量场景都必须走 GPU**（1 小时录音 CPU 要 16 分钟，其中 encode 占 5.4s/30s 窗口，是纯算力瓶颈）。
3. **冷启动很便宜**：模型加载 0.1–0.9s（磁盘 mmap）。这比我原先"冷启动可能几十秒"的担心乐观得多——**前提是模型常驻磁盘、进程按需拉起**，而不是每次重新下载。
4. encode 时间与音频长度**近似线性**（每个 30s 窗口一次），所以 RTF 对长音频是稳定的，可直接用于预算外推。

## ⚠️ 意外收获：CPU 基线直接复现了我们要解决的问题

用 `ggml-base` 转写 4.4s 原始素材，输出是：

```
[00:00:00.000 --> 00:00:04.500]  幫我把這段的褲子拔出來
```

三个问题一次性暴露，正好是 PRD 的动机：

1. **没有时间轴**：整段 4.4s 被塞进**一个** segment——可它实际是"2s 哼唱 + 2s 语音"。哼唱段被 ASR 直接**幻觉**成了语音内容。
2. **意图与目标分离**：真正要处理的是 00:00–02:00 的哼唱，但 ASR 只吐了一句话，上层完全看不出"有个跨段的请求"。
3. **领域词错**：`谱子` → `褲子`（且输出繁体）。→ 支持 L1-plus 与"ASR prompt hint"的价值。

→ 这就是 **PRD §4.2「预检必须覆盖全时长」+「时序分类是核心」** 的实测依据：**不做 SED 分段，ASR 会把非语音段吃掉并编出内容。**

# T1 补充 · VAD 对照实验（2026-09-10）

用 whisper.cpp 内置 VAD（`ggml-silero-v6.2.0.bin`，来自 HF **`ggml-org/whisper-vad`** 仓库）对同一 4.4s 素材重跑：

| 配置 | 输出 | 时间戳 |
|---|---|---|
| base（无 VAD） | `幫我把這段的褲子拔出來` | `00:00.000 → 04.500`（一整段） |
| base + VAD | `幫我把這段的譜字發出來` | `01.990 → 04.420` ✅ |
| turbo + VAD | `帮我把这段的普姿扒出来` | `01.990 → 04.420` ✅ |

VAD 自身的判定：

```
VAD segments: 1  →  start = 1.99, end = 4.42  (2.40s)
Reduced audio from 70266 to 38425 samples (45.3% reduction)
vad time = 6.98 ms
```

## 两个分离的结论

**① 结构问题：是管线问题，不是模型问题，一个 VAD 就修好了。**

- 不用 VAD：整段 4.4s 塞进一个 segment，**哼唱段被幻觉成语音**，时间戳完全错。
- 加 VAD：**切点 1.99s 与真值 2.00s 只差 0.01s**，哼唱段被正确排除，时间戳回到真实位置。
- VAD 本体只花 **7 ms**（885KB 模型，CPU）。
- → 直接验证 PRD §4.2「预检必须先分段、时序分类是核心」。**这一层不需要大模型，也不需要 GPU。**

**② 词错问题：换大模型救不回来，说明该换的是"语种专精模型 + 领域提示"。**

- `谱子` → base `褲子`/`譜字`，turbo `普姿` —— **turbo（809M）并没有比 base 好**，甚至更离谱。
- 这不是算力问题：whisper 系在中文上本来就偏弱。
- → 两个推论：
  1. **floor 不该选 whisper**，应选中文专精模型（SenseVoiceSmall / Paraformer-zh）；whisper 只适合当多语兜底。
  2. **L1-plus 的收益要重新评估**：与其"换更大的 whisper"，不如先上 **ASR prompt hint / 领域词表**（whisper 有 `--prompt`，`-nt/--carry-initial-prompt` 可常驻）。这条应进 PRD §11 B.3 的候选排序。

# T1 补充 2 · GPU（CUDA）结果 — 2026-09-10

二进制：`whisper-cublas-12.4.0-bin-x64.zip`（b4938，随包 cuBLAS/cuDART 12.4）
素材：`m0_long_26s.wav`（26.3s）

## 结果

| 配置 | 总耗时 | 倍速 | 备注 |
|---|---|---|---|
| base / CPU (8线程) | 735 ms | 36× | |
| base / GPU | 622 ms | 42× | 小模型上 GPU 几乎没收益 |
| turbo / CPU (8线程) | 6958 ms | 3.8× | |
| **turbo / GPU · 第 1 次（冷）** | **41902 ms** | 0.63× | ⚠️ 见下 |
| **turbo / GPU · 第 2 次（热）** | **1385 ms** | **19×** | |

turbo 热跑分项：encode **142.6 ms**（CPU 是 5363 ms → **37×**）、decode 73.6 ms、batchd 155.8 ms。
**峰值显存：2758 MiB。**
模型加载 941 ms。终端显示 `CUDA : ARCHS = 500,610,700,750,800,860,890,900` —— **列表里没有 sm_120**。

## 三个结论

**① prebuilt CUDA 包在 sm_120 上「能用」，但靠的是 PTX JIT。**

ARCHS 里没有 120，第一次跑 CUDA 内核时驱动现场 JIT 编译，**首跑多花了约 40 秒**（41.9s vs 1.4s）。
好消息：JIT 结果进了驱动的 Compute Cache，**之后再起的进程就不重编了**（第 2 次是独立进程，1.4s）。
坏消息：**这个 40 秒的代价会在驱动升级 / 缓存被清后重现**——对"按需拉起"的部署模式是个隐患，需要在健康检查里覆盖。

**② 热跑之后 GPU 确实碾压 CPU，而且优势全在 encode。**

turbo：**19× 实时**（CPU 只有 3.8×），encode 单项快 **37 倍**。换算 1 小时音频：GPU 约 **3.2 分钟**，CPU 约 16 分钟。
→ **PRD Q2「L1-plus 的延迟预算」有了硬数字**：只要 JIT 缓存热着，升级到 GPU 是 ~5× 端到端收益（计算部分 37×）。

**③ 小模型上 GPU 不值得。**

base 在 GPU 上只快 15%（622 vs 735 ms）。→ 印证 PRD §11 B.2/B.4：**floor 用小模型放 CPU 就够，不该占用 GPU**；GPU 的收益要模型大到 turbo 这个量级才开始显现。

# T1 终章 · 原生 sm_120 构建（CUDA 13.4.1 + VS2026）— 2026-09-10 16:35

工具链：VS 18 Community (MSVC 19.51) + CUDA **13.4.1** (V13.4.59) + cmake 4.4.3 + Ninja
构建：`cmake -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=120`

后端自报：

```
CUDA : ARCHS = 1200 | BLACKWELL_NATIVE_FP4 = 1
```

## 对照结果（同一素材 26.3s，large-v3-turbo）

| | 预编译包（靠 PTX JIT） | **原生 sm_120 构建** |
|---|---|---|
| **首次运行（全新进程）** | **41902 ms** ⚠️ | **1356 ms** ✅ |
| 热跑总时 | 1385 ms | **1210 ms** |
| encode | 142.6 ms | **89.0 ms**（1.6×） |
| 模型加载 | 941 ms | 894 ms |

## 结论

1. **那 40 秒的首跑 JIT 惩罚彻底消失**：首跑 41.9s → **1.36s**（30 倍）。
   之前预编译包只带 sm_90 的 cubin，Blackwell 内核靠驱动现场编译；现在是原生 cubin。
   → 对"按需拉起"的部署模式，**这个隐患消除了**，健康检查不必再为驱动更新后首跑变慢做兜底。
2. **encode 快 1.6×**（142.6 → 89.0 ms），说明 JIT 出来的内核本来也不如原生。
3. 总时受**模型加载（~0.9s）**主导——短音频场景下加载占七成。**这印证了"进程常驻/预热窗口"的价值**：
   真要用 L1-plus，进程不该每次冷启。
4. 有效吞吐 ≈ **21.8× 实时**（1210 ms / 26.35s）。
