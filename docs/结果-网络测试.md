# 网络吞吐排查（2026-09-10）

## 结论（修正版）

**Mac ↔ seanartech-lab 的链路完全正常，能跑到 2.2 Gbit/s。**
之前测到的 5–28 MB/s **全部是 SSH 测量假象**（Windows OpenSSH + MSYS 管道），与网络无关。

### 纯 TCP 实测（`tools/tcpbench.py`，完全不经 SSH）

| 方向 | 1 流 | 4 流 | 8 流 |
|---|---|---|---|
| PC → Mac | 186 MB/s (1488 Mbit/s) | 189 | **188.7 (1509 Mbit/s)** |
| Mac → PC | **278 MB/s (2224 Mbit/s)** | 276 | **278.7 (2230 Mbit/s)** |

- **Mac → PC 基本打满 2.5G 网口（2230 Mbit/s）** ✅
- PC → Mac 稳定在 ~1500 Mbit/s；加到 8 并发也不涨 → 疑似 **Windows 侧 Python 发送端** 的瓶颈（非网络），需 iperf3 复核
- 方向不对称（2230 vs 1509）符合"Windows Python 发送比 macOS 慢"的预期

### 同样是纯 TCP，但用 SSH(SFTP/管道) 时

| 目标 | 上传 Mac→X | 下载 X→Mac |
|---|---|---|
| 老笔记本 .201（Realtek 1G） | 93.8 / 107.7 MB/s | 11.8 / 47.3 MB/s |
| seanartech-lab 主机 .200 | 27.7 / 36.6 MB/s | 7.8 / 31.3 MB/s |
| VM 100.64.0.6（Linux，同物理口） | 28.6 / 33.6 MB/s | 56.2 / 64.4 MB/s |

→ 这张表**衡量的是"ssh 隧道 + MSYS 管道"的端到端吞吐**，不是网络能力。seanartech-lab 的 sshd 组合特别差（27.7 vs 老笔记本的 93.8）。

## 教训

1. **别用 scp/ssh 管道测网速**，更别用它搬大文件。要用 `tcpbench.py` 或 iperf3。
2. **把"某段链路是百兆"这类结论建立在 SSH 数字上是危险的** —— 本次就是一个反向案例（曾误判为交换机上联百兆 / Hyper-V vSwitch 瓶颈）。
3. macOS 的 iperf3/原生 socket 可以作为基准端；Windows 侧建议用 iperf3（C 实现）而非 Python 复测。

## 实用建议

- 搬模型/数据集：**不要走 scp**。走 SMB 共享、Gitea/LFS(HTTPS)、或 `tcpbench` 式的原生 TCP 通道。
- 复测：`tools/tcpbench.py serve`（一端）+ `tools/tcpbench.py client <ip> --dir both --parallel 8`

## 工具

- `tools/nettest.sh` — 走 SSH 的快速对比（方便，但含 SSH 开销）
- `tools/tcpbench.py` — 零依赖原生 TCP 测量（**推荐**）

# 修正 #2（2026-09-10 16:30）——两件事，别混为一谈

用户插拔了「交换机→墙插」的网线后网速恢复。复盘时间线：

| 时间 | 测试方式 | 结果 |
|---|---|---|
| 16:07 | **原生 TCP**（Mac 起 HTTP server，PC 用 curl 拉） | **11.2 MB/s** ← 当时网络本身就慢 |
| 16:07 | SSH | 10.3–11.1 MB/s |
| 16:24（插拔后） | **原生 TCP**（tcpbench） | **278 MB/s（2230 Mbit/s）** |
| 16:26（插拔后） | SSH | 上传 22–33 MB/s / 下载 7.9 MB/s |

## 结论（两条独立的问题）

**① 11 MB/s 那次 = 线松了。** 证据是 16:07 那次**原生 TCP 的 HTTP 测试同样只有 11.2 MB/s**——
没有 SSH 参与也慢，所以当时就是链路问题。插拔后原生 TCP 直接到 2.2 Gbit/s。
网卡错误计数也干净（PC：ReceivedPacketErrors 0；Mac en6 无 IERR/OERR）。

**② SSH 路径另有瓶颈，与线无关。** 插拔之后原生 TCP 278 MB/s，而同一时段 SSH 只有 22–33/7.9 MB/s。
同样的 SSH 测法在老笔记本上能到 93.8 MB/s → 是 **seanartech-lab 上 Windows OpenSSH + MSYS 管道**的问题，不是网络。

> 之前第 1 版文档把全部现象都归给 SSH —— **那个结论是错的**，因为漏看了 16:07 那次原生 TCP 同样慢。

## 实用结论

1. **网络没毛病**：原生 TCP 双向 1.5–2.2 Gbit/s，2.5G 网口基本打满。
2. **搬大文件到 seanartech-lab 不要用 scp/ssh**（慢 6–35 倍）。用 **SMB 共享** 或 Gitea/LFS(HTTPS)。
3. 想进一步查 SSH 那个瓶颈：可以试试用 PowerShell 直接往 stdout 写（绕开 MSYS），看能不能恢复。
