# T2 结果 · Mac 本地 floor（VAD + SenseVoiceSmall）

> 2026-09-10 · MacBook Air **Apple M1 / 8 核 / 16 GB**
> 运行时：`sherpa-onnx 1.13.7`（ONNX Runtime，**无 torch**）+ Python 3.13
> 模型：`SenseVoiceSmall` **int8，239 MB**（HF `csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`）
> VAD：`silero_vad.onnx` 644 KB
> 线程：4

## 结果

| # | 配置 | 素材 | 端到端（不含加载） | 倍速 |
|---|---|---|---|---|
| A | VAD + SenseVoice | 4.4s | 259 ms | 16.9× |
| B | 裸跑 SenseVoice（无 VAD） | 4.4s | 274 ms | 16.0× |
| C | VAD + SenseVoice | 26.3s | **1248 ms** | **21.1×** |

分解（26.3s 素材）：recognizer 加载 **1106 ms**｜VAD **115 ms**｜ASR 合计 1133 ms。

## 最重要的结果：词全对了

| 模型 | 输出 |
|---|---|
| whisper base（CPU） | `幫我把這段的褲子拔出來` ❌ |
| whisper **turbo**（CPU / GPU） | `帮我把这段的普姿扒出来` ❌ |
| **SenseVoiceSmall int8（M1 CPU，239MB，无 GPU）** | **`帮我把这段的谱子扒出来。`** ✅ |

→ **中文专精的小模型在 Mac 的 CPU 上，速度追平了 whisper-turbo 跑在 5070 Ti 上的水平（21× vs 19×），同时把词做对了，而且只要 239MB、不占 GPU。**

这条直接回答 PRD Q2：**L1-floor = SenseVoiceSmall int8，跑在 Mac CPU 上。**
换算 1 小时音频 ≈ **2.9 分钟**。

## VAD 表现

- 26.3s 素材（6 次重复「2s 哼唱 + 2s 语音」）→ **切出 6 段，每次都正确排除了哼唱段** ✅
- VAD 本体只花 **115 ms / 26s**（644KB 模型）
- ⚠️ **但切点偏晚**：sherpa 的 Silero VAD 切在 **2.18s**（真值 2.00s），把「帮」字吞了（所以 A/C 的第一段变成「我把这段…」）。
  对比 whisper.cpp 的内置 VAD 切在 **1.99s**（几乎完美）。
  → **需要给 VAD 加 speech padding / 调 `min_silence_duration`**，否则每段开头都会掉字。**这是必须修的第一个工程细节。**

## 意外收获：事件标签白送

SenseVoice 每条结果都附带：

```
lang=<|zh|>   emotion=<|NEUTRAL|>   event=<|Speech|>
```

- 这就是旧设计稿说的「SenseVoiceSmall 一个模型输出转写 + 情感 + 音频事件标签」。
- 但注意：**它是段级标签，不是帧级**——所以它能覆盖 AED 的一部分（"这段是什么"），**不能替代** PANNs/EfficientAT 的帧级路由（"第几秒切换"）。与 PRD §11 B.5 的判断一致。

## 结论

1. **floor 定案：Mac CPU + SenseVoiceSmall int8 + Silero VAD**，21× 实时，总计约 240MB 模型、无 torch、不占 GPU。
2. **whisper 可以退出 floor 了**，只保留为多语兜底（它中文弱，且唯一优势「MIT 许可」在本项目已不是约束）。
3. **VAD padding 是必须修的**（当前每段掉一个字）。
4. GPU（L1-plus）的价值现在要重新算：既然 Mac CPU 已经 21×，**plus 档的必要性主要落在"长音频/批量"上**，而不是"短音频质量"——因为质量短板已经被 SenseVoice 补上了。
