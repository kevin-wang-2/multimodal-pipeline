# T5 结果 · 文档 / 图像腿：三档 OCR 实测与多级管线建议（2026-09-17）

> 对应 [架构.md](架构.md) §11 的图像腿。
> 结论一句话：**文档 / 图像腿和音频腿同构，快档打全场、慢档按需升级；但升级粒度必须是"页 / 区域"而不是"整份"，而且 runner 必须排队。**

## 0. TL;DR

1. 三档 OCR 全部在 GPU 机（RTX 5070 Ti 16GB，Windows）上跑通，速度和能力差两个数量级：

| 档位 | 引擎 | 速度（GPU） | 显存 | 输出形态 |
|---|---|---|---|---|
| **快** | PP-OCRv6-medium（`paddleocr` 3.7） | **0.42–0.54 s/页** | 小（<2GB） | 纯文本行 |
| **中** | Tesseract 5.5（CPU 基线） | 1.05 s/页（M1 CPU） | — | 纯文本行 |
| **慢** | **PaddleOCR-VL 1.6（0.9B）** | **5.5–10.9 s/页（≈9s）** | **~12 GB** | Markdown/HTML + 版面元素标签 |

2. **"更快的新引擎"并没有解决"理解带格式文本"**：PP-OCRv6 在干净印刷体上 CER 1.11%，和 Tesseract 1.13% 基本打平；两者在同一张真扫描剧本页上都把人名输出成 `Gus./GUs./GUS.` 混用、舞台指示与对白不分。
3. **0.9B 文档 VLM（PaddleOCR-VL）才跨过了那条线**：人名统一成 `GUS.`、折行重排成段落、舞台指示单独成块、发票直接吐结构化表格、**印章被当作独立元素识别**（章文都读出来）。
4. 代价是 **~20× 慢 + 12GB 显存**。所以结论不是"换 VL"，而是：**快档预扫 → 发现"信息不够 / 信息混乱" → 只把可疑的页 / 区域升级给慢档**（铁律 1）。
5. **runner 排队是硬需求**：VL 单页吃 12/16GB，单卡并发只能是 1；快档可以并发 2–4。必须有队列 + 优先级 + 背压 + 幂等，否则一个批量任务就能把交互式请求饿死或把显存打爆。

## 1. 测试条件与口径

- 机器：GPU 机（RTX 5070 Ti 16GB / 驱动 610.88 / paddlepaddle-gpu 3.4.0 cu129，`run_check` 报 `Compute Capability 12.0` = sm_120）；CPU 对照为 Mac M1（8 核，当时机器负载很高）。
- 素材：
  - **真扫描剧本**：一部英文剧本的扫描件（47 页，每页 300dpi JPEG、零文本层），取 20 页。
  - **原生剧本栅格化**：另一部英文剧本（原生文本层）→ 300dpi 栅格化 20 页，**有 ground truth 可算 CER**（模拟"扫描件"）。
  - **中文电子发票**：真实增值税专票 3 张 → 300dpi 栅格化 → 字段对拍。
- 口径：CER 微平均用 difflib 编辑脚本（上界）；字段比对锚定"发票号码 / 开票日期 / 价税合计 / 合计金额"。
- ⚠️ **样本量很小**（真扫描 1 张代表性页面细看、发票 3 张、栅格化 20 页），结论方向可信，具体数字别当验收基准。

## 2. 实测结果

### 2.1 速度与成本

| 任务 | PP-OCRv6（GPU） | PP-OCRv6（CPU 24 核） | PaddleOCR-VL（GPU） |
|---|---|---|---|
| 发票（中文专票，300dpi） | 1.26 s/页 | 30–33 s/页 | ~10 s/页 |
| 剧本栅格化（英文，20 页） | 0.54 s/页（20 页 10.8s） | — | ~9 s/页 |
| 真扫描剧本（英文，20 页） | 0.42 s/页（20 页 8.4s） | — | 5.5–10.9 s/页 |

- GPU 相对同机 CPU：**约 25×**（发票口径）。
- VL 首次加载模型 ~76s，缓存后 ~5s；**加载 / 预热是真实成本**（和音频腿 GPU 档"模型加载占七成"的结论同构）。

### 2.2 能力对比（同一张真扫描剧本页）

| 维度 | Tesseract 5.5 | PP-OCRv6 | **PaddleOCR-VL 1.6** |
|---|---|---|---|
| 人名大小写 | `Gus./GuS./GUS.` 混乱 | 混乱 | **`GUS.` 统一** |
| 舞台指示 | 混在对白里 | 混在对白里 | **单独成块**（`Pause.` → `## Pause`） |
| 折行 | 保留原折行 | 保留原折行 | **重排成完整段落** |
| 输出 | 纯文本 | 纯文本 | **Markdown/HTML** |
| 版面元素标签 | 无 | 无 | `text / table / seal / image / figure_title / aside_text / vision_footnote` |

### 2.3 发票（中文）

- 字段级：PP-OCRv6 **3/3 张全对**（号码 / 日期 / 价税合计 / 合计金额）；VL 同样全对，且**输出结构可以直接入库**：

```
购买方信息 | 销售方信息
项目名称│规格型号│单位│数量│单价│金额│税率│税额
*供电*电费││度│1996.66666666667│1.0619469026549│2120.35│13%│275.65
合 计│…│¥2120.35│…│¥275.65
价税合计（大写）│ⓧ贰仟叁佰玖拾陆圆整 (小写) ¥2396.00
备注│购方开户银行…销方开户银行…
```

- **印章（"重叠"场景）**：VL 把印章识别成独立 `seal` 元素，并读出章文「全国统一发票监制章 / 国家税务总局 / ××市税务局」。**不需要先抠章**。
- 合成红章压字实验：章压在明细表区域时，关键字段仍全部读对；但**合成章没有真正盖住"价税合计"**，所以"压字"结论仍未成立，需要真实盖章扫描件复验。

### 2.4 鲁棒性：几何退化比噪声更致命

用同一页做劣化对照（Tesseract 口径）：

| 劣化 | CER |
|---|---|
| 干净 300dpi | 0.21% |
| 高斯噪声 / 模糊 / JPEG q25 / 降到 150dpi | 0.21–0.26%（**几乎不掉**） |
| 旋转 1.5° | 0.21% |
| **旋转 3°** | **62.6%**，且文字量从 1914 字掉到 **721 字**（静默丢内容！） |

→ **deskew / 去畸变的收益大于换模型**；而且失败模式是"静默丢内容"，不是报错，必须在管线里用"字符数 / 覆盖率异常"检测出来。

## 3. 能力边界

**现在就能做到**

- 印刷体、300dpi 级别的扫描件：字符级 CER 1% 量级。
- 发票 / 票据字段抽取：字段级基本可交付（快档就够）。
- 版面结构（标题 / 段落 / 表格 / 印章 / 图注）：**只有 VL 档能做到**。
- 多语言：PP-OCRv6 覆盖 50 语、VL 覆盖 100+ 语。

**现在还做不到 / 不能承诺**

- 手写体（开源最好也就 2.4–2.9% CER 的行级模型，中文手写更差）。
- 真实盖章压字后的字段级可靠性（缺真实样本）。
- 精确复刻排版（缩进量、字体字号、斜体），VL 给的是**语义版面**，不是印刷还原。
- 多栏 + 框线交错时的阅读顺序仍偶有错。

## 4. 多级管线设计（图像腿 ↔ 音频腿同构）

### 4.1 分层映射

| 层级 | 音频腿（已定） | 图像 / 文档腿 |
|---|---|---|
| **L0**（常开、永远注入） | VAD 定界 + 打标标签 | **版面粗分**：页数、是否可判定为"扫描件"、方向 / 歪斜角度、文本密度 |
| **L1-cpu**（便宜档） | SenseVoiceSmall int8 + Silero VAD | **Tesseract / PP-OCR 小模型 CPU**：保证"有字可读"，慢但不依赖 GPU |
| **L1-gpu** | whisper.cpp 原生 sm_120 | **PP-OCRv6（GPU）**：0.4–0.5 s/页，全量预扫的主力 |
| **L2**（按需、用完卸载） | 扒谱 / 分轨 / 声纹 | **PaddleOCR-VL 1.6（0.9B）**：版面 + 结构 + 印章；**只跑可疑页 / 区域** |
| **L3**（最后手段） | 原生多模态模型整轮接管 | 同上 |

### 4.2 升级触发信号（文档版）

快档跑完后，**只有这些信号才值得升级**：

- **置信度**：行级识别置信度低于阈值，或低置信行占比超阈值。
- **覆盖异常**：OCR 出来的字符数 / 文本行数相对"版面预估"明显偏低（对应旋转 3° 那种静默丢内容）。
- **结构信号缺失**：页面明显有表格 / 图 / 印章，但快档输出里没有任何结构标签（快档本来就没有，所以这条更多是"按页面类型预判要不要上 VL"）。
- **几何异常**：L0 报出歪斜角度超阈值、多栏 / 双页拼版、非文本区域占比异常。
- **语言 / 字体异常**：命中未覆盖语种、竖排、特殊字体。
- **上层显式要求**：用户追问细节、上下文矛盾、"这不是我看到的"。

### 4.3 升级粒度：页 / 区域级，而不是整份重跑

- 一份 100 页文档，只有 3 页是复杂表格 → **只把这 3 页交给 L2**，其余走快档结果。
- 同一页内也可以只升级"表格区域 / 印章区域"（VL 的版面模型会给出区域框）。
- 好处：延迟与成本随"可疑量"增长，而不是随文档长度线性增长（和音频腿"调用次数随段数增长、不随时长"的原则完全一致）。

### 4.4 缓存与幂等（与音频腿同构）

- 缓存键 = **内容 hash + 页范围 + 引擎档位（tier / engine_version）+ 参数**。
- **档位必须进键**，否则"便宜档跑过一次"会永久挡住 GPU 升级路径。
- 升级结果要**标注来源层级**（"此段来自 L2 重分析"），让上层知道信息换了来源。

### 4.5 降级链

```
VL（L2）失败 / OOM → PP-OCRv6 GPU（L1-gpu）
PP-OCRv6 不可用 → CPU 便宜档（L1-cpu）
本服务不可用 → 调用方自行兜底 / 明确声明"本次未做识别"
```

每一档都要在 digest 里写明"本次降级"，禁止静默失败。

## 5. runner 与调度：排队是刚需，不是优化

### 5.1 显存决定并发上限

- **VL：单页峰值 ~12 GB / 16 GB** → **单卡并发 = 1**（并发上去直接 OOM）。
- PP-OCRv6：显存占用小 → 单卡并发 2–4 可接受。
- 结论：**同一张卡上"慢档"和"快档"不能自由混跑**，必须由调度器串行化慢档、控制总并发。

### 5.2 队列语义

- 任务 = `(content_hash, page_range, tier, engine_version, params)`，天然幂等（同键同结果，可去重合并）。
- **优先级**：交互式（用户正在等）> 预扫批处理；批量任务必须让路。
- **背压**：队列长度上限 + 拒绝策略（返回"排队中 + 预估时间"而不是超时）。
- **超时**：按 tier 设（快档秒级；VL 单页 10s 级，超时回落快档结果）。
- **可观测**：每任务记录 tier、耗时、是否降级、gaps。

### 5.3 预热

- VL 冷启加载 ~76s（缓存后 ~5s）→ **必须常驻或预热窗口**，否则"按需拉起"的成本会吃掉收益（和音频腿 GPU 档的结论一致）。
- 若做不到常驻，则"升级"应当允许**异步**：先给上层快档 digest（标注"已排队 L2 升级"），升级完成后再注入一次。

### 5.4 与整体架构的关系

- 这些需求直接成为 [架构.md](架构.md) §7「A 内部：队列、缓存、引擎池」的依据。
- "先出快档 digest、异步补一份 VL 的"是双轨问题在图像腿上的翻版。**建议 MVP 阶段只做"按需升级"，不做自动双轨**，避免"同一媒体两份 digest"的版本问题。

## 6. 复现

- 环境：Windows + conda（Python 3.12 + paddlepaddle-gpu 3.4.0 cu129 + paddleocr 3.7.0 + paddlex 3.7.2）。
- 脚本（尚未迁入本仓库 `tools/`，待整理）：`render_pdf.py` 栅格化 + 真值、`ocr_paddle.py` PP-OCR 批跑、`ocr_vl.py` VL 管线、`inv_eval.py` 字段对拍、`eval_cer.py` CER、`seal_overlay.py` 合成章。
- 关键安装坑（避免重踩）：
  1. **pip 在 Windows 上会读注册表里的系统代理** → 几百 MB 的轮子必卡死；改用 `curl` 分片并行下载 + `pip --no-index --find-links` 离线装。
  2. `nvidia-nvjitlink-cu12` 在 cufft / cusolver / cusparse 的 METADATA 里**不带版本号**，pip 会直接报 `Could not find a version`。
  3. paddle CPU + oneDNN 会炸（`ConvertPirAttribute2RuntimeAttribute`）→ `FLAGS_use_mkldnn=0`；**GPU 不需要这个开关**。
  4. VL 管线要 `paddlex[ocr]` 而不是 `paddlex[ocr-core]`；模型走 ModelScope（`PADDLE_PDX_MODEL_SOURCE=modelscope`）可达 33 MB/s。

## 7. 未尽事项

- **样本量小**：真扫描页只细看 1 页；发票 3 张；"结构化还原率"没有量化。
- **压字实验未成立**：合成章没盖住关键字段，需要**真实盖章扫描件**。
- **未试的档位**：GLM-OCR（0.9B，约 1.86 页/秒，可能兼顾速度与结构）、MinerU 2.5-Pro（AGPL，学术长文）、dots.ocr（给坐标）。
- **未量化**：多栏 / 双页拼版的阅读顺序错误率；手写体；中英混排。
- 下一步：① 剧本整本 20 页过 VL，量化"结构还原率"；② 真实盖章件做压字回归；③ 把"快扫 + 按需升级"做成 runner 的可跑原型（含队列与背压）。
