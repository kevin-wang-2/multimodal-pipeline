# 架构

> 状态：设计定稿，M1 实现中（S0–S2、S4、S5 引擎部分已完成，2026-09-21）
> 本文是设计的公开版本。私有的部署拓扑、决策理由与商业上下文不在此文。

## 0. 一句话

一个**独立的多模态感知服务**：媒体附件进来，先用一组小模型自动产出**结构化 digest**（时间轴 + 原子事实 + 缺口 + 可用能力清单），交给上层 agent 消费；agent 据此判断"信息够不够"，不够再按需调用更贵的能力，这些能力**可能反过来再调用本服务**。

## 1. 目标与非目标

**目标**

1. 媒体进来自动产出结构化 digest，上层 agent 永远只消费文本。
2. 上层 agent 能拿 digest 自行判定信息是否充分，并自行选择下一步能力。
3. 信息按成本分层解锁：默认只跑便宜的，贵的按需。
4. 平台无关：核心逻辑是可独立部署的服务，换平台只重写薄适配层。
5. 模态同构：音频先跑通，图片 / 视频复用同一套抽象。

**非目标**

- 不做 latent alignment、不训 adaptor 接主模型。文本是 LLM 的原生模态，零对齐成本。
- 不做实时流式语音。
- 不做媒体生成（生成类能力可以作为任务类型挂上来，但不是本服务的目标）。
- 不追求"理解无损"，本方案本质是有损压缩，只保证**可升级**。
- 不提供托管服务。协议与实现可自建（headscale 类比），但不做多租户、配额、计费。

## 2. 设计铁律

1. **信息分层 / 预算阶梯**：便宜路径永远可用，贵路径按需解锁。
2. **预检只产出任务无关的原子事实**。"信息够不够"永远是任务相关的判断，归上层 agent。
   - 反例（禁止）："这是一段需要扒谱的哼唱"。
   - 正例："00:00–02:00 无伴奏人声哼唱，基频约 200–400 Hz"。
3. **预检必须覆盖全时长**。用户意图可能藏在另一个时间段里（02:00–04:00 说的那句话，决定了 00:00–02:00 那段该怎么处理）。禁止"先猜重点段再分析"。
4. **放弃猜意图，就必须全面 + 诚实**。digest 要主动暴露 gaps、失败的工具、低置信度段落。
5. **本服务不承诺可用性；兜底是调用方的事**。它是分布式服务，算力节点可以关机、连接可以断。服务的义务只有两条：失败与超时必须可见（明确的错误码 / 任务状态，绝不静默），以及结果必须标注来源与档位。
6. **原始媒体引用必须保留**。它是所有升级路径的弹药库；digest 只是索引，不是替代品。
7. **核心逻辑与平台解耦**。服务只暴露"媒体进 → 结构化文本出"的接口；任何 hook / 插件机制都属于适配层。
8. **格式转换用确定性模板，不用 LLM 总结**（例外见 §14 开放问题）。
9. **接口通用，实现专用**。任何调用方可见的契约（任务 API、媒体句柄、结果 schema、能力注册表）不编码网络拓扑、存储厂商或机器名；实现层可以放心专用，不为不存在的第二个部署买单。

## 3. 三个角色

```
A 算力节点 ──(主动出站 ws：注册能力 / 心跳 / 收请求)──▶ B 协调节点 ◀──(任务 API)── C 调用节点
  模型是 A 的插件                                    无状态：注册表 + 转发           agent 侧客户端包
  队列 / 缓存 / 引擎池都在 A                          可与 A 或 C 同进程
```

| 角色 | 职责 | 语言 | 状态 |
|---|---|---|---|
| **A 算力节点** | 任务执行：队列、缓存、引擎池、任务类型注册表；对外只有一条出站 ws | Python | 有状态（队列、缓存） |
| **B 协调节点** | 接受 A 的注册与心跳；接受 C 的任务请求；按能力挑 A、转发、透传结果；认证 | 一套协议，两个实现：Python（绑 A）、TypeScript（绑 C / 独立） | 无状态 |
| **C 调用节点** | agent 侧适配层：提交任务、等结果、注入 digest、兜底 | TypeScript 包 | 无 |

### 3.1 B 是角色，不是部署单元

逻辑上 B 永远存在，物理上默认绑定：

- **A/B 绑定**：B-py 跑在 A 进程内，只监听内网地址。A→B 的"长连接"退化为进程内调用，但走同一接口。内网可达的 C 直连它。
- **B/C 绑定**：B-ts 跑在公网 agent 宿主的进程内，暴露一个带认证的 ws 端点给 A 连入。这是系统里**唯一的公网监听**，而且在公网侧，不在内网。
- **独立 B**：多 A 多 C 互不相识时才需要；届时 B-ts 单独部署，A 与 C 都不用改。
- A 可以同时连多个 B。

### 3.2 拓扑约束

- **A 零公网监听**。A→B 只有主动出站的认证 ws。**不允许任何形式的端口映射**（frp、`ssh -R`、cloudflared 一律不用）：端口映射即暴露。
- **内网不暴露到公网，公网不进内网。** 满足这条的唯一方式就是上一条。
- 跨国 / 跨云的媒体不走裸流，走对象存储 + 媒体句柄（§6）。

### 3.3 预检与能力是同一套任务系统

预检只是**自动触发**的任务类型（如 `triage.audio`、`triage.image`），能力是 agent **显式调用**的任务类型（如 `ocr.structured`、`pitch_transcribe`、生成类）。它们共用队列、缓存、媒体句柄与结果格式。给 agent 的 skill 封装只是"提交任务、等结果"的薄壳。

## 4. A↔B 协议（ws + JSON，语言中立）

> 定稿见 [协议.md](协议.md) §2 与 `protocol/schemas/ab-message.schema.json`。本节只讲形状。

一条连接，四类消息：

```
A → B   register   { node_id, capabilities: [<§10 元数据>], engine_versions, auth }
A → B   heartbeat  { node_id, queue_len, vram_free_mb, engines_loaded }
B → A   request    { req_id, job: <§5 的 /jobs 请求体> }     # 提交 / 查询 / 取消都是 request
A → B   response   { req_id, http_status, body }               # 与 §5 的 HTTP 语义一一对应
```

- **B 无状态**：只有"已连接 A""能力表""在途 req_id → 等待方"三张内存表。B 重启只丢在途请求，C 重试。
- 路由：C 请求 `type=X` → B 在能力表里找能做 X 的 A → 多个则按 `queue_len` 挑；无 → 对 C 回 `503 no_node`。
- A 断线：在途请求回 `503 node_offline`；A 重连即重新 `register`。
- A/B 绑定时这四类消息就是进程内函数调用，接口相同。
- 认证：`register` 携带节点密钥；B 校验后才接受能力表。

## 5. C→B 任务 API（一套，异步）

> 定稿（含错误码表、取消语义、状态机）见 [协议.md](协议.md) §3–§4 与 `protocol/schemas/job-api.schema.json`。

只有一种调用形态：**提交即返回任务 id，可选 `wait` 秒数做长轮询**。缓存命中与短任务在 `wait` 内直接拿到结果；长任务客户端再按 id 轮询。不分"同步 / 异步"两套。

```
POST /jobs
  { "type": "triage.audio" | "ocr.structured" | …,
    "media": <媒体句柄，§6>,
    "params": {...},                 # 类型专有参数：领域词、目标段落等
    "tier": "cpu" | "gpu-fast" | "gpu" | "remote",   # 可选，档位偏好
    "priority": "interactive" | "batch",
    "wait": 5 }                      # 可选，最长阻塞秒数
  → 200 { "job_id", "status": "done", "result": <digest 或能力输出>, "cached": true|false }
  → 202 { "job_id", "status": "queued" | "running", "eta_sec", "queue_position" }
  → 429 { "error": "backpressure", "retry_after_sec" }          # 来自 A，B 透传
  → 503 { "error": "no_node" | "node_offline" }                  # 来自 B

GET    /jobs/{id}[?wait=N]
DELETE /jobs/{id}                  # 取消
GET    /capabilities               # B 汇总各 A 的任务类型注册表（§10）
GET    /health                     # B：已连接 A 及其心跳摘要
```

- 预检返回 **digest JSON（§8）**；能力任务返回该类型注册的 `output_schema`。大输出不内联，PUT 到媒体句柄的输出端点，响应里只给引用。
- 每个结果都带 `source.engine` / `source.tier` / `cached`；失败任务带明确错误码。**没有静默失败**。
- C 永远不知道 B 是绑定的还是远端的。
- 核心包只依赖标准 HTTP / ws，不绑供应商 SDK；配置全部外置；依赖声明式（manifest）。

## 6. 媒体句柄（一种契约，多种实例）

```
"media": {
  "inline": "<base64>",                                  # 小媒体；或
  "get": { "url": "...", "headers": {...} },              # 带认证的 GET 端点
  "put": { "url": "...", "headers": {...} }               # 可选：大输出的 PUT 端点
}
```

- A 只做 HTTP GET / PUT，**不认识任何存储厂商**。对象存储的 presigned URL、宿主自己的带 token 接口、将来 B 提供的上传口，都是这个契约的实例。
- 内容 hash 在 A 取到字节后统一计算，作为 `media_id` 与缓存键，**与来源无关**：同一份媒体经内联与经 URL 提交命中同一条缓存。
- "本机路径"不在契约里。它只在三者同进程时有意义，进契约会污染接口。
- 原始媒体引用（铁律 6）就是这个句柄；digest 里回指它。
- 句柄由 C 的宿主签发。通用情况下 C 可能没有存储，那时由 B 提供上传入口，先不做，契约已留位。

## 7. A 内部：队列、缓存、引擎池

这是 M1 要交付的东西，**模型只是往里注册**。

**队列是刚需**。实测（[T5](结果-T5-文档OCR.md)）文档 VLM 单页占约 12GB / 16GB 显存，单卡并发只能是 1；批量任务与交互式预检会抢同一张卡。必须：

- 优先级：`interactive` > `batch`，批量任务让路；
- 背压：队列长度上限，超限返回 429 + `retry_after`，而不是超时；
- 幂等：任务键 = (内容 hash, 任务类型, 引擎档位, 引擎版本, 参数)，同键合并；
- 超时：按任务类型设（预检秒级；VLM 单页 10s 级），超时回落便宜档并在结果里标注。

**引擎池**：显存感知；引擎档位（tier）是 A 内部概念：

- CPU 便宜档：`Silero VAD + SenseVoiceSmall int8 + Zipformer AudioTagging int8`（全 ONNX，零 torch，约 270MB，[T2](结果-T2.md)）；
- GPU 档：whisper.cpp（原生 sm_120 构建，[T1](结果-T1.md)）、PP-OCRv6、PaddleOCR-VL 等（[T5](结果-T5-文档OCR.md)）；
- 重模型按需装卸，加载成本计入调度（VLM 冷加载约 76s / 缓存后约 5s；whisper 加载 0.9s 占短音频总时七成，所以要常驻或预热窗口）。

**缓存键 = 内容 hash + 任务类型 + 引擎档位 + 参数**。只用 hash 的话，先用便宜档跑过的媒体之后永远命中旧结果，升级路径会被缓存堵死。缓存里同时记档位，允许"升级重算"。

**可观测**：每任务记录 tier、各阶段耗时（`timings_ms`）、是否降级、gaps；心跳里上报队列长度与显存。

## 8. digest schema（核心产出物）

```json
{
  "media_id": "sha256:6b4a2b8c89e0bcf240920e7922d8d77666f7b61a11ba2ba7389f8156986220f1",
  "kind": "audio",
  "duration_sec": 4.392,
  "timeline_unit": "sec",
  "segments": [
    {"start": 0.0, "end": 2.182,
     "labels": [], "label_status": "unclassified",
     "asr": null},
    {"start": 2.182, "end": 4.384,
     "labels": [{"tag": "Speech", "score": 0.735}], "label_status": "ok",
     "asr": {"text": "我把这段的谱子扒出来。", "lang": "zh", "confidence": "n/a"}}
  ],
  "global": {"speech_ratio": 0.501},
  "tools": {"vad": "ok", "audio_tagging": "ok", "asr": "ok"},
  "gaps": [
    "0.00–2.18s 为非语音段，但分类置信度过低（top 0.118 < 阈值 0.30）→ 无法判定类别",
    "结构事实：非语音段位于时间轴前部、语音段在后（指令在后）"
  ],
  "capabilities_available": ["pitch_transcribe", "chord_recognize", "source_separate", "denoise", "speaker_id", "music_id", "transcribe_segment"],
  "source": {"tier": "cpu", "engine": "silero-vad+sensevoice-int8+zipformer-tagging-int8", "engine_version": "m0-2026-09-10",
             "generated_at": "2026-09-10T17:00:00+08:00", "degraded": false, "params": {"label_confidence_threshold": 0.3}},
  "timings_ms": {"vad": 45, "tagging": 12, "asr": 210}
}
```

这份样本就是 `protocol/fixtures/digest/root/valid/m0_hum_then_speech.json`，字段边界由 `protocol/schemas/digest.schema.json` 说死（[协议.md](协议.md) §7）。`cached` 不在 `source` 里：命中缓存是本次交付的属性，放在任务响应顶层。

要点（均由 [T4](结果-T4.md) 盲测得出）：

- `segments` 是**唯一的时间轴事实源**，所有能力的输出都要能挂回它。
- `gaps` 是显式的"我还不知道什么"，是上层 agent 判断够不够的主要依据。盲测实例正是靠 `gaps` 里那条结构提示做对了判断，**它是核心字段，不是装饰**。
- **低置信度不下结论**：设 `label_confidence_threshold`（拟 0.30）。低于阈值 → `labels: []` + `label_status: "unclassified"`，并把"无法判定类别"写进 `gaps`。禁止把 0.118 分的标签当事实。
- **不要用 `null` 表示"不知道"**：`null` 只表示"该字段对本段不适用"（如非语音段没有 asr）。取不到的值用 `"n/a"` 或省略字段；"不知道"一律走 `gaps`。
- **便宜档不设 `caption`**。需要描述时它是 `capabilities_available` 里的一项可选能力。
- **预检只负责"路由"，不供给"执行数据"**。音高 / 调性 / 速度 / 乐器等属于被调能力的执行产物，不进 digest；digest 唯一必须交给下游的是原始媒体引用。盲测原话："够用来选工具，但不够用来真正扒谱"，这正是应有的边界。
- `capabilities_available` 是**任务无关的能力清单**（"这段媒体上能做什么"），不是"我认为你要做什么"。它是能力发现机制，省掉把全套工具塞进系统提示。
- `tools` 里失败项必须显式标注；`source.engine` 必须记录是哪个引擎、哪一档产出的，否则同一媒体两次得到不同质量的描述无法归因。

## 9. 时间轴约定

- 统一单位：**秒（浮点）**；字段 `start` / `end`；区间**左闭右开** `[start, end)`。
- 所有能力的输出必须可映射回同一时间轴；各自的帧号 / 采样点编号在适配层内消化掉。
- 打标粒度约 0.5s 一点，段级切分足够；能力需要更细粒度时自行下钻，但输出仍锚回 `[start, end)`。
- **这是整个系统最容易埋雷的地方，第一天就定死。**

## 10. 任务类型注册表与能力发现

每个任务类型在 A 的注册表里带元数据，A 注册到 B 时整表上报：

```yaml
id: pitch_transcribe
modal: audio
consumes: { labels: [Humming, Singing], granularity: segment }
tier: gpu             # cpu / gpu / remote
cost: low
latency_hint: "~2s"
input: { media: required, start: required, end: required }
output_schema: "note_list | midi"
```

- 预检结束时按媒体特征筛出候选清单塞进 `capabilities_available`。
- 新增能力不用改预检代码；上层按能力名从 `/capabilities` 按需拉详细说明，避免全量工具描述占满上下文。

## 11. 预检层（音频腿，已实测定型）

- **定界** → Silero VAD（帧级、极便宜，7–45ms）
- **打标** → clip 级 AudioSet tagger，只对 VAD 切出的**段**各跑一次（次数随段数增长，不随时长）
- **ASR** → SenseVoiceSmall int8（中文强，附带段级事件标签）

原则：

- **不要用密集滑窗做长音频**（1 小时 × 0.2s 步进 ≈ 8 分钟）。
- **路由只用粗类别 + 置信度**，并设阈值；细粒度标签不可信（合成哼唱被标成 `Dog`）。
- **时序切分是核心**：整段分类在"先说一句话、再放纯音乐"这种场景会判错。
- **成本控制即分层**：先分段，只对 speech 段跑 ASR，只对 music 段跑音乐能力。

图像 / 文档腿的同构设计见 [T5](结果-T5-文档OCR.md) §4：快档预扫全场，只把可疑的**页 / 区域**升级给慢档。

## 12. 预算阶梯与反馈升级

```
L0        VAD / 打标标签              常开，永远注入
L1-cpu    CPU 便宜档 ASR / 指纹        服务在线即可用，按段触发
L1-gpu    GPU 档                       延迟预算内时优先，提质
L2        重分析（更大模型 / VLM）      按需：用户追问 / 低置信度 / 上下文矛盾
L3        整轮接管（原生多模态模型）    最后手段，由调用方直接调，不经本服务
```

- 升级触发信号：**显式**（"你理解错了""再看一遍"）最强；**隐式**（低置信度、上下文矛盾、追问细节但注入不足）。
- 防死循环：记录"该媒体已升级次数"并设上限；升级结果**标注来源与层级**，让上层知道信息已换来源。
- 升级结果仍是文本注入，状态永远归上层。

## 13. 失败与降级

- 降级链：预检正常 → 预检部分失败（出 digest 骨架 + gaps）→ 服务不可用 / 超时 → **调用方自行兜底**（平台转写 / 纯文本）。前两级归服务，后两级归调用方。
- **降级必须显式**：注入块里写明"本次预检降级，无时间轴信息"。
- A 断连、B 无节点、队列超限，都是明确的错误码（§5），不是挂死。
